# テスト計画

- 対象：見積もり・請求 練習帳（見積もりから請求書までを扱う小さな Web アプリ。リポジトリ名・worker 名は mitsumori）
- テストの根拠：[仕様書](spec.md)。仕様の決まりは、項目 ID（`S-...`）で引用する。
- 作成日：2026-11-21（アプリを作り始める前に書いた）
- 下書き：Claude Code（AI）。テストの方針と中身を決めるのはオーナー（3 章）。
- 関連：[テスト設計](test-design.md)、テストケース一覧（`tests/cases.csv`）、結果レポート（`docs/test-report.md`）

## 方針の決定（2026-11-21）

Claude Code が選択肢と推奨案を示し、オーナーが選んで決めた。

- 自動化の方針（7 章）：決まり（計算・日付・入力・状態）は単体テストで網羅する。画面テストは、画面の流れ・表示・つなぎ込みを代表の値で確かめる。見た目と操作感は、iPhone 実機の手動テストで確かめる。理由：速くて毎回同じ結果になる単体テストで数を担い、時間のかかる画面テストは利用者の流れに絞る。機械では良し悪しを決めにくい見た目は、人が見る。
- 試す値の選び方（境界値、デシジョンテーブルの絞り方）の決定は、[テスト設計](test-design.md)の「方針の決定」に書いた。

## 1. 目的

- 仕様書に書いた決まりのとおりにアプリが動くかを、テストで確かめる。
- テストを自動化し、変更のたびに自動で回して、その記録を残す。
- テストは仕様書だけをもとに設計する。アプリより先にテスト計画・テスト設計・テストケース一覧を作り、その順番をコミットの履歴に残す。

## 2. 進める順番と成果物

1. 仕様書（`docs/spec.md`）
2. テスト計画（この文書）
3. テスト設計（`docs/test-design.md`）：技法ごとに、何をどう試すかとその理由
4. テストケース一覧（`tests/cases.csv`）：ID、観点、技法、前提、手順、期待結果、自動/手動、優先度
5. アプリを作る（ここで初めてアプリができる）
6. 自動テスト：ケース一覧から作る単体テストと画面テスト
7. 自動実行：変更のたびに GitHub Actions でテストを回す
8. 手動テスト：iPhone 実機で確かめ、結果をケース一覧に記録する
9. 不具合の記録（GitHub の Issue）と結果レポート（`docs/test-report.md`）

## 3. 役割分担

| 作業 | 担当 |
|---|---|
| アプリのコード、テストのコード | Claude Code（AI） |
| テスト計画・テスト設計・テストケース一覧・結果レポートの下書き | Claude Code（AI） |
| テストの方針と中身を決めて直す（どの値を試すか、何を自動にして何を手で確かめるか、優先度） | オーナー |
| iPhone 実機での手動テストと、その結果の記録 | オーナー |
| 不具合の報告（GitHub の Issue） | 手動テストで見つけたものはオーナーが書く。自動テストで見つけたものは Claude Code が下書きし、オーナーが確かめてから出す |

## 4. 2 つの層のテスト

テストを 2 つの層に分ける。混ぜると、開発中の普通の失敗と、テストで見つけた不具合の区別がつかなくなるため。

| | 作る側のテスト | テスト担当のテスト |
|---|---|---|
| いつ書くか | アプリを作りながら | アプリができたあと |
| 何から作るか | 作る人が、作りながら決まりを確かめるために書く | 仕様書 → テスト設計 → テストケース一覧から作る |
| ケース ID | なし | `TC-<分野>-<3 桁>`（例：`TC-CALC-012`）。分野は仕様書に合わせる。テストの名前の先頭に付ける |
| 落ちたとき | 開発中の普通の失敗。直して進む。不具合として報告しない | 原因を調べて振り分ける（11 章）。アプリの不具合なら、GitHub の Issue にする |
| 道具 | Vitest | Vitest（単体テスト）、Playwright（画面テスト）、iPhone 実機（手動テスト） |

- テスト担当のテストを、作る側のテストとは別に作る理由：作る人は自分の作り方に合わせてテストを書きがちで、仕様を読み違えていると、実装とテストが同じように間違えるため。
- 不具合として Issue にするのは、テスト担当のテストで見つかったものだけ。見つかった件数は 0 件でもよい。その場合は、0 件だったことと、何を試して 0 件だったかを結果レポートに正直に書く。

## 5. 範囲

仕様書のすべての分野をテストする。お金と期限にかかわる決まり（計算・日付・状態）と入力チェックは、間違えると業務で一番困るため、重点にする。ケースごとの優先度は、テストケース一覧でオーナーが決める。

| 分野 | 仕様 | 主に確かめること | 重点 |
|---|---|---|---|
| 計算 | S-CALC | 税率ごとの対象額と税額、端数の切り捨て、値引き、合計、大きな金額 | 高 |
| 日付 | S-DATE | 有効期限、支払期限、期限切れ、日本時間で決める「今日」 | 高 |
| 状態 | S-ST | 下書き → 発行済み → 請求済み、期限切れ、できない操作が本当にできないこと | 高 |
| 入力 | S-INP | 数値の読み取り、文字数、行数、値引きの上限、誤りの文言と件数、発行の条件 | 高 |
| 番号 | S-NUM | 順番、重複と欠番がないこと、桁が増えるところ | 中 |
| 保存 | S-STO | 自動保存、保存できないとき、壊れた保存データ | 中 |
| 画面・表示 | S-SCR、S-DISP | 画面の行き来、一覧、金額と日付の形、文言、iPhone の幅 | 中 |
| 見た目・操作感 | S-DISP-06、S-SCR-11 | 帳票らしい見た目、iPhone での使いやすさ | 中（手動） |

## 6. やらないこと

- この版で作らない機能のテスト（S-OUT-01〜S-OUT-06）：ログイン・サーバー・同期、マスタ管理、PDF と印刷、値引きの割り振り、インボイスの記載事項、英語。機能がないので、テストもしない。ただし「状態を戻す操作がないこと」（S-OUT-07、S-ST-11）は確かめる。
- 【削る候補】の機能を作らなかった場合、その機能のテスト（S-STO-06、S-STO-07、S-STO-10〜S-STO-12）。仕様書に「この版では作らない」と書き、テスト設計からも外す。
- 性能（速さ、大量のデータ）、セキュリティ、アクセシビリティの網羅的な確認。
- Chromium と WebKit 以外のブラウザ（Firefox など）、Android、iPad。
- 複数のタブで同じデータを同時に編集したときの動き（仕様に決まりがないため）。
- 公開 URL での全件のテスト。公開 URL では、1 日 1 回の短い確認だけを行う（8 章）。

## 7. 自動化するものと、手で確かめるもの

| 何を | どこで | 理由 |
|---|---|---|
| 決まり（計算・日付・入力の読み取りとチェック・状態・番号） | 単体テスト（Vitest） | 組み合わせが多いので、速く、毎回同じ結果になる単体テストで網羅する |
| 画面の流れ（新しい見積もり → 発行 → 請求書）、ボタンや入力欄の出る・出ない、文言、保存と読み込み直し、決まりが画面につながっていること（代表の値で） | 画面テスト（Playwright。Chromium と WebKit の両方） | 利用者と同じ操作で確かめる。時間がかかるので、決まりの網羅は単体テストに任せる |
| 見た目（帳票らしさ、崩れ）、iPhone での操作感 | 手動テスト（オーナー、iPhone 実機） | 良し悪しを機械では決めにくい。Playwright の WebKit は、実機の Safari と同じではない |

手動テストで確かめること（ケースの細かい中身はテストケース一覧で決める）：

- 見た目が事務用の帳票らしく落ち着いていて、崩れていないこと（S-DISP-06）。
- 実機の画面幅で、ページ全体が横にスクロールしないこと（S-SCR-11。375px 幅そのものは、画面テストで幅を 375px にして確かめる）。
- 日本語キーボードで全角の数字や、絵文字を入れたときの動き（S-INP-11、S-INP-14）。
- 入力欄を押したときに画面が勝手に拡大されないか、ボタンを押しやすいかなどの操作感。
- ホーム画面に追加したアプリでも開けて、保存が残ること（S-STO-01）。
- 削除の確認ダイアログが実機でも出ること（S-ST-10）。

自動テストの書き方：

- 画面の操作は、画面ごとの部品（Page Object）にまとめる。画面の作りが変わっても、直す場所が 1 か所で済むため。
- 自動テストの名前の先頭にケース ID を付ける（例：`TC-CALC-012 税率ごとに端数を1回だけ切り捨てる`）。
- 日付は固定する。単体テストでは「今日」を外から与え、画面テストでは Playwright の時計の機能を使う。実行する日によって結果が変わらないようにするため。
- 端末の時刻帯を変えて実行する（9 章）。日本時間で日付を決める決まり（S-DATE-01）を確かめるため。
- テストごとに、保存データが空の状態から始める。前のテストの影響を受けないようにするため。
- テストのデータはすべて架空にする。実在の会社名・人名・取引は使わない。
- ケースとコードの対応を確かめる小さなスクリプトを作る。ケース一覧で「自動」になっている ID がすべてテストコードにあるか、逆にテストコードにある ID がすべてケース一覧にあるかを確かめる。

## 8. 自動実行

- push と pull request のたびに（GitHub Actions）：lint、型チェック、単体テスト、ビルド、画面テスト（Chromium と WebKit）、ケースとコードの対応の確認。
- 1 日 1 回：公開 URL に対して短い確認テストを行う（主な画面が開き、見積もりから請求書まで一通り進めるか）。
- Playwright の HTML レポートを、実行結果として残す。README のバッジで、最新の結果がわかるようにする。

## 9. 環境

| 環境 | 中身 | 使うテスト | 主に確かめること |
|---|---|---|---|
| Chromium（デスクトップ） | Playwright のデスクトップ用 Chrome 相当 | 画面テスト（自動） | 画面テストのすべて |
| WebKit（iPhone 15 相当） | Playwright の WebKit と、iPhone 15 の端末設定（画面の大きさ、タッチ） | 画面テスト（自動） | 画面テストのすべてを、iPhone に近い条件で |
| iPhone 実機の Safari | オーナーの iPhone | 手動テスト | 見た目、操作感、日本語キーボードでの入力 |
| iPhone 実機のホーム画面アプリ | 同じ iPhone で「ホーム画面に追加」したもの | 手動テスト | 開けること、保存が残ること、見た目 |
| Node.js | Vitest | 単体テスト | 決まり |

- 端末の時刻帯：日本（Asia/Tokyo）、UTC、日本より進んだ時刻帯（Pacific/Auckland）で試す。
- 自動テストは、オーナーの Windows の PC と GitHub Actions で実行する。
- 実機の機種と iOS の版は、手動テストを行ったときに記録する。

## 10. 合格の基準

- 単体テストがすべて通り、画面テストが両方のブラウザ（Chromium と WebKit）ですべて通る。
- 続けて 3 回実行して、毎回同じ結果になる（ときどき落ちる不安定なテストがない）。
- ケース一覧で「自動」になっているケースの 100% が、テストコードと対応している。

## 11. 不具合の扱い

テスト担当のテストが落ちたら、すぐに Issue にせず、まず原因を調べて次のどれかに振り分ける。

| 原因 | 扱い |
|---|---|
| アプリの不具合 | 不具合として GitHub の Issue にする |
| テストのコードの誤り | テストのコードを直す。不具合にはしない |
| 仕様のあいまいさ | 「仕様の確認」のラベルを付けた Issue にし、オーナーが決める |

- 期待結果は、オーナーの同意なしに、テストを通すために変えない。
- 不具合の Issue の内容は、再現手順、期待結果、実際の結果、環境、必要なら画面写真。
- 実際に見つかったものだけを書く。作り話の不具合や、実際には回していないテストの結果は載せない。
- 直した不具合は、もう一度テストを回して直ったことを確かめる。直さないと決めたものは、結果レポートに「残ったリスク」として書く。

## 12. リスク

| リスク | 起こると困ること | 対策 |
|---|---|---|
| アプリとテストの下書きを、同じ AI（Claude Code）が書く | 同じ思い込みで、実装とテストが同じように間違え、誤りに気づけない | テストは仕様書だけから、アプリより先に設計する。オーナーが中身を確かめて直す |
| 日付と時刻に頼るテスト | 実行する日や時刻によって、結果が変わる | 日付を固定する（7 章） |
| 自動実行の環境（GitHub Actions）は UTC で動く | 時刻帯の扱いの誤りを見逃す。または、偽の失敗が出る | 時刻帯を指定して、日本・UTC・日本より進んだ時刻帯で試す |
| Playwright の WebKit は、iPhone の Safari と同じではない | 実機でだけ起きる不具合を見逃す | 実機で手動テストをする |
| iPhone 15 相当の画面は 393px 幅で、仕様の 375px より広い | 375px 幅での崩れを見逃す | 375px 幅の確認は、画面の幅を 375px にして別に行う |
| 実機では、保存の失敗を起こしにくい（プライベートブラウズでも保存できることが多い） | 保存できないときの動き（S-STO-03〜S-STO-05）を確かめられない | 自動テストで、保存をわざと失敗させて確かめる |
| iPhone のホーム画面アプリと Safari では、保存データが別になる | 不具合ではないものを、不具合と取り違える | Safari とホーム画面アプリを、それぞれ別の環境として確かめる |
| ときどき落ちる不安定なテスト | テストの結果を信用できなくなる | 決まった時間だけ待つ書き方をせず、画面の表示を待つ。3 回続けて同じ結果になることを合格の基準にする（10 章） |
| 期限が 1 週間で、アプリ作りに時間を取られる | テストが薄くなる | アプリの機能を削る（仕様書の【削る候補】）。テストは削らない |
| 仕様のあいまいさ | 何を期待結果にすればよいか決められない | テスト設計で見つけた 4 つは、仕様書に書き足して解決した（テスト設計 7 章）。テスト中に見つけたものは、「仕様の確認」の Issue にする（11 章） |
